# Quality Checker Policy

このプロジェクトでは、品質チェッカーの実行自体を省略しない。

## 基本方針

- チェッカーは、特別な互換性問題や既知の重大な回帰がない限り最新版を使用する。
- Error は修正必須とする。
- Warning / Attention も原則として設計改善の対象とし、単に「CIが通るから」という理由で無視しない。
- 特に UPD Commander Checker の Container 化・責務分割・入出力整理などの提案は、実行時コストが十分小さい場合は原則として従う。

## 性能上の例外

以下のように、提案へ従うことで実行時コストやアルゴリズム局所性が明確に悪化する場合は例外を認める。

- ホットパスで一時オブジェクト生成が大量に増える。
- 単純な値受け渡しが過剰な Container / DTO 化によって重くなる。
- 重要な計算が複数モジュール・複数クラスへ分裂し、呼び出しや間接参照のコストが無視できない。
- リアルタイム処理で、設計上の分割より局所性を保つ方が明確に有利である。

例外はできるだけ rule / path / line 単位に限定し、理由をコメントまたは ignore 設定に残す。プロジェクト全体や広いディレクトリを丸ごと除外する方法は最後の手段とする。

## CI運用

- lint / format / type check / tests / smoke / dependency check / design checker / runtime performance check はすべて実行する。
- チェッカーに severity や rule 単位の CI gate 設定がある場合は、それを使用して通常の Warning / Attention も修正対象として扱う。
- 必要な設定機能が自作チェッカーに存在しない場合、その場しのぎでチェック自体を無効化せず、チェッカー本体のリポジトリへ Issue を作成する。
- upstream が対応するまでの局所例外は、性能上または互換性上の理由を明記する。
- 既存違反が多いチェッカーを新規導入する場合もチェッカー自体は必須実行する。必要なら一時baselineを置き、新規悪化を禁止しながらbaselineを段階的に0へ下げる。
- baselineは既存違反を恒久的に許可する仕組みではない。改善時は上限も下げ、追跡Issueを完了するまで残件を管理する。

## バージョン方針

品質チェッカーは原則 latest-first とする。固定版を使用するのは、最新版に以下のような明確な問題が確認された場合だけとする。

- CIが実行不能になる回帰
- 誤検出により通常開発が成立しない
- サポート対象環境との互換性破壊

固定する場合は、固定理由と解除条件をこのディレクトリ内の文書または Issue に残す。
