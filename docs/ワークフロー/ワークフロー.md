# 1回の開発ワークフロー

この文書は、1つのIssueに着手してPull Requestを作成し、通常開発の `work` へ取り込むまでの手順を定める。
開発予定・評価フィードバック・進捗の正本は GitHub Issues とする。

https://github.com/tomiya7688/obake-no-sumika/issues

## 手順

1. 作業ツリーを確認する。`git status --short --branch` を実行し、未関連の変更がある場合はステージング・削除・上書きをしない。
2. リモート変更を取り込む。`git fetch origin` の後、`work` へ切り替え、`git merge --ff-only origin/work` を実行する。未関連のローカル変更と競合する場合は取り込まず、解決方法を確認する。
3. [Issue優先度方針](Issue優先度.md)に従い、`gh issue list --state open --label P0` で緊急対応を確認する。通常作業では `gh issue list --search "コンテキスト OR context"` でコンテキスト削減関連を先に読み、P1 → P2 → P3と依存関係から対象を選ぶ。P4は着手前に再分類する。`gh issue view <番号>` で対象Issueの完了条件を読む。
4. `work` から `issue/<番号>-<短い名前>` の作業ブランチを作る。
5. Issueの完了条件に沿って、テスト可能な最小単位を実装する。深い設計が必要な場合だけ機能説明書を更新する。
6. 対象テスト、全体テスト、必要な実行確認を行う。変更履歴が必要な場合は `docs/ver.md` を更新する。
7. 今回の変更だけを明示的にステージングし、コミットして作業ブランチをpushする。
8. `gh pr create` で `work` 宛てのPull Requestを作成する。完了するIssueは `Closes #番号`、部分対応は `Refs #番号` と本文に書く。
9. 差分を自己レビューし、最新のPRレビュー・コメントとIssueの指摘を確認する。下記のレビュー方針に従って `work` へマージする。
10. マージ後にIssueの完了条件を確認する。全条件を満たした場合だけIssueをCloseし、次回の作業は手順1から始める。

## レビューと取り込みの方針

- 通常開発の `work` 宛てPRは、自己レビュー・テスト・必要な検証を行い、届いている指摘を確認してから取り込む。Kadoka本人からレビューや保留指示が来ていなければ、本人の承認を待つだけで止めず、マージして次の作業へ進む。返信待ちの期限や、毎回の追加承認は設けない。
- 後からの不具合・改善フィードバックはKadokaがIssueで登録し、後続の作業として優先度と依存関係に従って扱う。レビュー未着だけを理由にPRをDraftのまま残さない。
- 既に届いている要修正の指摘、失敗している必須チェック、既知の重大問題は無視しない。明示的な保留指示やブランチ保護も尊重する。未確認項目はPRへ記録し、検証済みとは報告しない。Issueの完了条件を満たしていなければCloseしない。
- リリース前の確認は例外とし、Kadokaの確認・承認を待つ。通常開発の取り込み許可を、`main` への反映・タグ作成・リリース公開の許可として扱わない。

## ルール

- GitHubのIssue、Pull Request、レビュー、リリース操作は `gh` CLI を利用する。
- Issueがない作業は原則開始しない。緊急修正は作業直後にIssueを補記する。
- IssueにはP0〜P4を1つだけ付ける。新規は原則P2、優先案件はP1、P0は緊急復旧に限る。
- 1 Issueはテスト可能な単位まで小さく保つ。
