# 開発ワークフロー

開発予定・評価フィードバック・進捗の正本は GitHub Issues です。
https://github.com/tomiya7688/obake-no-sumika/issues

## 評価者

1. 対象の機能・画面・データを確認する。
2. 既存 Issue を確認し、重複がなければ Issue を作成する。
3. 再現手順、期待結果、実際の結果、確認環境を記載する。

## 実装者（Codex を含む）

1. `gh issue list` と対象 Issue を確認する。
2. `work` から `issue/<番号>-<短い名前>` の作業ブランチを作る。
3. Issue の完了条件に沿って実装する。深い設計が必要な場合は機能説明書も更新する。
4. 対象テスト、全体テスト、必要な実行確認を行う。
5. 変更履歴が必要な場合は `docs/ver.md` を更新する。
6. コミットし、作業ブランチを GitHub へ push する。
7. `work` 宛ての Pull Request を作成し、本文に `Closes #番号` を記載する。
8. 承認後に `work` へマージし、Issue の完了条件を確認して Close する。

## リリース

1. `work` の内容を確認して `main` 宛ての Pull Request を作成する。
2. 承認・マージ後、バージョンタグとリリースノートを作成する。
3. GitHub 上のリリース内容と配布物を確認する。

## ルール

- Issue がない作業は原則開始しない。緊急修正は作業直後に Issue を補記する。
- 未関連の作業ツリー変更はステージング・削除・上書きしない。
- 1 Issue は、テスト可能な単位まで小さく保つ。
