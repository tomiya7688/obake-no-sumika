# Issue優先度方針

優先度の正本はGitHub Issueに付ける `P0`〜`P4` ラベルとする。小さい数字ほど先に取り組む。通常の高優先度案件はP1とし、P0は緊急対応のために基本的に空けておく。

| ラベル | 位置づけ | 判断基準・例 |
| --- | --- | --- |
| P0 | 緊急対応 | 現在進行中の重大な障害・データ消失など、通常作業を中断して復旧が必要な案件 |
| P1 | 優先 | 優先的に進める機能・基盤整備、重要な不具合、直近の作業を妨げる問題 |
| P2 | 通常（既定） | 通常の機能追加、改善、不具合修正、保守 |
| P3 | 後回し可 | 影響が限定的な改善・不具合、当面の作業を妨げず後に回せる整備 |
| P4 | 将来 | 将来の構想・拡張。現在の開発対象には入れず、着手する時に優先度を見直す |

## 付け方・見直し

- 未完了Issueには優先度ラベルを必ず1つ付ける。複数のPラベルを併用しない。`bug` や `documentation` などの種類ラベルとは併用できる。
- 新規Issueは原則P2から始め、影響・緊急性・現在の開発方針に応じて変更する。未分類Issueがあれば、着手判断の前に分類する。
- 不具合であること、重要な機能であること、ユーザーから依頼されたことだけでP0にしない。P0には緊急事象・影響・復旧条件をIssue本文に書く。
- 緊急対応が終わったら、完了条件・マージ・検証を確認してCloseするか、残作業に応じてP1〜P4へ変更する。P0のまま通常の追加改善を続けない。
- 優先度を変更する場合は理由をIssue本文またはコメントに残す。ラベルは進捗や重大度そのものを表さず、変更しても完了条件は消さない。
- 依存待ちだけを理由にP3/P4へ下げない。高優先度案件の前提が未完了なら、その前提を先に進め、対象Issueへ関係を記録する。
- P4は却下・Closeを意味しない。将来着手する時にP1〜P3へ移す。

## 1回の作業での選び方

1. 現在の障害・P0を確認し、緊急復旧が必要なら先に対応する。
2. 通常作業ではコンテキスト削減関連Issueを先に読み、今回の読み方・作業範囲に適用する。先に読むことと、必ず先に実装することは分ける。
3. ユーザーの明示した作業対象と依存関係を確認し、P1 → P2 → P3の順で着手可能な最小単位を選ぶ。同じ優先度では前提作業を先に進める。
4. P4は将来候補として保持し、着手するなら先に優先度を見直す。

ラベルごとの一覧は `gh issue list --state open --label P1 --limit 100` のように確認する。未完了Issue一覧はこの文書に転記せず、GitHub上で管理する。
