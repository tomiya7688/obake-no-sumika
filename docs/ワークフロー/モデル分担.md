# モデル分担と助言役の呼び方

品質を保ったまま、使用量を減らすための分担。本人指示（2026-11-06）で、Anthropic が公開している「メインは Sonnet、判断の節目だけ Opus に相談、調査は Haiku」という構成を参考に、このプロジェクト向けに組んだ。[共同作業ルール](共同作業ルール.md) と [役割別ワークフロー](役割別ワークフロー.md) の続き。

節約するのは、次の2つだけ。**品質ゲート（CI、[レビュー基準](レビュー基準.md)、外部レビュー、実画面確認、本人の承認）は緩めない**（「変えないもの」の節）。

- 高い判断力が要らない作業に、高いモデルを使うこと。
- 長い出力を、主担当の会話に流し込むこと。

## 分担

| 担当 | モデル | 仕事 | 定義の場所 |
| --- | --- | --- | --- |
| 主担当（メインのセッション） | Sonnet 5.5 | 実装・編集・PR・CI 対応・レビュー役 | 起動時の設定（本人の環境。「起動方法」の節） |
| 助言役 | Opus 5.5（advisor） | 判断の節目の相談だけ | 同上 |
| 調査 `search` / `grep` / `docs` | Haiku（読み取り専用） | 構造・呼出元・設計書や API の要約を調べ、結論だけ返す | 本人のユーザー設定 `~/.claude/agents/`（このリポジトリには置かない。二重管理しない） |
| 役割 `obake-implementer` / `obake-reviewer` / `obake-verifier` / `obake-triage` / `obake-rules-keeper` | sonnet（固定） | [役割別ワークフロー](役割別ワークフロー.md) の各役割 | `.claude/agents/` |

- 役割の定義は `model: sonnet` に固定する。親のセッションが Opus で動いていても、役割ごとのサブエージェントは Sonnet で動き、使用量が膨らまない。
- レビュー役を Haiku にしない。Haiku へのレビュー依頼は停止中（`AGENTS.md` の配布ブロック `no-haiku-review`）。Haiku は読み取り専用の調査にだけ使う。
- 役割の定義は `disallowedTools: Agent` を付け、サブエージェントから別のサブエージェントを起動させない（入れ子禁止）。
- 調査エージェントが無い環境では、読み取り専用の組み込みエージェント（Explore など）で代える。調査を主担当の会話の中で、ファイルを大量に読んで行わない。

## 助言役（Opus）を呼ぶ時点

助言役は、会話の全履歴（すべてのツール呼び出しと結果）を受け取って助言する。呼ぶたびに助言役のモデルのトークンを使い、履歴が長いほど高くつく。呼ぶ回数の上限の仕組みは無いので、次の3つの時点だけにする（目安: 1 Issue あたり 2〜3 回）。

1. **方針を固める前**: Issue と対象のコードを読み終え、実装や設計を書き始める前。
2. **同じエラーが2回出たとき**: 同じ失敗を繰り返していて、収束しないとき。
3. **「完了」と言う前**: 成果をコミット・push して残してから（呼び出しの最中にセッションが終わっても、成果が残るように）。PR を作る前、またはマージを判断する前。

呼ばない場面: 読み取りだけの調査、整形・文書の定型の更新などの機械的な作業、CI や外部レビューの待ち、ツールの出力で次の操作が決まる短い作業。

助言役が「よい」と言っても、CI の成功と外部レビューの記録は省略しない。助言役は判断の質を上げるもので、品質ゲートの代わりにはならない。助言と、すでに調べた事実が食い違う時は、黙って切り替えず、食い違いを書いてもう一度相談する。

## 機械的に決まる分岐は、既存のスクリプトに任せる

「どのファイルか」「どのテストか」「整形は済んだか」のように、考えなくても決まる分岐は、大きなモデルに考えさせず、すでにあるスクリプトで決める。

| 分岐 | 使うもの |
| --- | --- |
| 変更するファイルから、読む文書と回すテストを選ぶ | `tools/context/script/select_files.py`（責務表 `tools/context/responsibilities.json`） |
| 整形してよいか・済んだか | `tools/quality/script/format_changed.py --staged`（`--check`） |
| 全体の合否 | `scripts/evaluate_project.py --require-godot --frames 900`（CI も同じ） |
| 再試行するか・省略するか | [共同作業ルール](共同作業ルール.md) と [レビュー基準](レビュー基準.md): 再試行しない。省略は今回の証拠つきで記録する |

投稿にある「JEV」は、採用しない。出典を確認できない外部の製品名で、このプロジェクトのツールにも無く、検証できないため。同じ狙いは、上のスクリプトで満たす。

## 使用量を減らす運用

この数日の作業で、使用量を押し上げた実績のあるものへの対策だけを書く。

- **長い出力を主担当に流さない**: `Select-String` や `--jq` で必要な行に絞る。広い調査は調査エージェントに頼み、結論だけ（40行以内）受け取る。ログはファイルに書き、必要な行だけ読む。
- **待つ処理は通知を待つ**: バックグラウンドの処理は完了の通知を待ち、何度も状態を問い合わせない。
- **外部レビューの資料は 12,000 文字以内**: 文字数で数える（日本語は1文字が3バイトなので、バイトで測ると実際より大きく出る）。同じ資料を再送しない。使えない相手は1回で省略として記録し、再試行しない。
- **ローカルの全体評価が環境のせいで終わらない時**: PC が重く Godot の確認が時間切れになる時は、PR にその理由を書き、同じ評価を行う CI（Godot 4.7.2 つき）の結果を根拠にする。ポーリングしない。
- **画面のレイアウトのテストは、固定のピクセルで書かない**: Linux の CI は文字が広い。部品の要求サイズから計算した大きさで確かめる（固定値で書いて、CI で3回やり直した実績がある）。
- **文脈が長くなったら、新しいセッションへ引き継ぐ**: 目安は使用量の6割。助言役は全履歴を受け取るので、長い会話ほど相談が高くつく。

## 変えないもの（品質）

- Work CI の成功確認（失敗したらマージしない）。
- 外部レビュー（必須6者、追加の無料レビュアー、PR 時の CodeRabbit）の依頼と記録。使えない相手は、証拠つきで省略し、成功とは書かない。
- 整形、関連テスト、全体評価、UI を変えた時の実画面確認（本人に頼む時は確認キット）。
- `main` への反映・タグ・リリースの、本人の承認。
- 役割ごとの定義と、共有文書の食い違いは、共有文書を正として直す。

## 起動方法

助言役は、Anthropic API の実験機能。公式ドキュメント（`https://code.claude.com/docs/en/advisor`）で確認できたこと:

- 起動時に `claude --model sonnet --advisor opus`、起動後に `/advisor opus`、常用するなら settings.json の `"advisorModel": "opus"`。切るのは `/advisor off`。
- 組み合わせの表がある（メインに対して、助言役は同順位か上）。Bedrock / Vertex / Foundry では使えない。
- 呼ぶ時点はモデルの判断で、強制する仕組みは無い。だから、この文書のルールで、呼ぶ時点を決める。

これは本人の環境の設定なので、このリポジトリでは `settings.json` を変えない。
